## 1. 목표와 설계 경계

### 1.1 사용자 요구

실제 시작점은 PNU↔주소 변환의 업무상 필요다. 이를 지역코드↔명칭, PNU 부분 추출, 지역 내 토지·건물 주소 목록, 위치·공간·속성 연계로 확장한다.

국내 시도·시군구·읍면동·리 체계를 기본으로 하며, 다섯 입력 영역은 **주소·지명 / 코드 / 공간데이터 / 비공간 속성 / 위치·좌표**다. 건물관리번호는 선택적인 원천 식별자일 뿐 필수 허브가 아니다.

첫 사용 경험은 ‘입력 → 필요한 단계·열 선택 → 결과 검토 → 복사·다운로드’다. 지도는 공간정보가 있을 때 제공하는 확인 수단이며 코드 변환의 선행 조건이 아니다.

### 1.2 이번 문서가 고정하는 것

웹과 MCP는 같은 처리 함수를 호출한다. 코드·식별자는 문자열로 다룬다. 법정구역·행정구역을 분리한다. 원본 행, 후보 관계, 출처, 기준일을 보존한다. 원천 미확보를 ‘검색 결과 없음’으로 처리하지 않는다. 기존 시각화 기능을 회귀시키지 않는다.

### 1.3 개발 중 바꾸어도 되는 것

세부 화면 배치, 저장 엔진, 인덱스, 파일 파서, 수집 실행 도구, 작업 병렬도는 측정·검증 결과에 따라 바꿀 수 있다. 단, 변경 이유와 호환성 영향을 기록한다.

별도 Spring Boot·FastAPI 서버, Redis·Airflow, 새 프런트엔드 프레임워크, 전면적인 공용 작업 플랫폼은 초기 필수 사항이 아니다. 현재 구조에서 해결되지 않는 요구가 확인될 때 도입을 판단한다.

## 2. 최신 저장소 확인 결과와 통합 판단

### 2.1 확인 범위

기준 커밋의 프로젝트 목록, 루트 화면, 상단 탐색, 패키지·Nuxt 설정, 타입, 업로드 화면, 작업·임시 파일 처리, MCP 서버·앱, 검사 스크립트와 README를 확인했다. 코드 정적 검토이며 빌드·실서비스·AI 호스트 실행 검증은 수행하지 않았다. README의 실행 실적은 저장소의 자체 기록이지 이번 검토의 재측정 결과가 아니다. [R01–R11]

### 2.2 반드시 피할 잘못된 재사용

`shared/catalog/`는 확장자별 처리 정의를 자동 수집한다. 주소·코드 사전이나 수집 어댑터를 그 아래에 놓으면 기존 카탈로그 탐색과 충돌할 수 있다. 신규 도메인은 `shared/link/`로 분리한다. [R03]

기존 `Job`을 주소 변환까지 표현하도록 한 번에 대수술하거나 `format: 'address/pnu'`를 만들어 기존 Docker 파이프라인을 호출하지 않는다. 문자열 분해·지역명 조회에 Docker·PostGIS·지도 서버가 필수로 뜨는 구조를 만들지 않는다. [R04][R05]

### 2.3 현재 코드에서 확인한 공개 운영 점검 항목

`stageUrl()` 주석에는 DNS 확인과 실제 요청 사이의 변경을 막지 못하는 한계가 명시되어 있다. 새로운 기능에서 외부 URL 입력을 제공할 경우 이를 그대로 안전하다고 전제하지 않는다. 초기에는 직접 업로드 중심으로 시작하거나 네트워크 차단·요청 IP 고정 등 검증된 방어를 적용한다. [R06]

작업 UUID는 경로 검증 수단이지 사용자 권한 확인의 대체물이 아니다. 공개 배포 시 작업 소유권, 허용된 다운로드, 로컬 파일 경로 금지, 신뢰 가능한 외부 URL 구성이 확인되어야 한다. 이번 검토는 전체 저장소 보안 감사가 아니므로 발견하지 못한 경로가 안전하다고 단정하지 않는다.

## 3. 사이트 구조와 사용자 흐름

### 3.1 경로와 메뉴

`/`는 두 도구를 소개한다. 기존 통계는 시각화 카탈로그에서 계산된 값이라는 의미를 유지하고, 주소 변환 건수를 형식·레시피 수에 섞지 않는다.

`/viz/**`는 기존 기능을 유지한다. `/link`는 새 도구의 기본 작업 화면이다. `/link/regions`는 지역명·코드·상하위 구역 탐색, `/link/data`는 지원 자료와 기준일·상태를 보여주는 신규 경로의 기본안이다. 단순 탭으로 시작해도 된다.

`/ai`는 공용 연결 안내로 유지한다. `/mcp`는 하나를 유지한다. ‘MCP 서버 하나’는 ‘HTML UI 리소스도 반드시 하나’라는 뜻이 아니다. 기존 앱을 보존하고 새 연계 화면을 별도 리소스로 등록하는 방식을 우선한다. [R07][S05]

### 3.2 기본 작업 화면

기본 화면의 순서는 입력, 출력 설정, 실행, 결과 표다. 대량 파일은 ‘파일 선택 → 컬럼 선택 → 일부 미리보기 → 실행’으로 진행한다. 단순 붙여넣기에는 컬럼 선택 단계를 생략한다.

출력 설정은 작업 종류, 구역 기준, 단계, 코드 표현, 주소 표현, 선택 열로 나눈다. 상세 옵션은 접어두고 최근 설정을 재사용할 수 있도록 한다. 기본은 원본 행 유지, 중복 유지, 실패 행 유지다.

결과 표에는 원본 값, 출력값, 처리 상태, 확인 수준을 먼저 보여준다. 후보 목록·처리 근거·원천 정보는 상세 영역에서 확인한다. 키보드만으로 입력·옵션 선택·결과 복사가 가능하도록 한다.

### 3.3 핵심 시나리오

**PNU 목록 변환:** 목록 붙여넣기 → 읍면동까지 선택 → 코드·지역명 출력 → 오류 행 확인 → 복사.

**주소 파일의 코드 추가:** CSV·XLSX 업로드 → 주소 컬럼 지정 → 법정구역·지번 파싱 → 복수 후보 선택 → PNU 형식값을 원본 열 옆에 추가.

**구역별 목록 추출:** 지역코드·지역명 입력 → 토지 또는 건물 선택 → 데이터 범위·기준일 확인 → 조건 적용 → 주소 목록·객체 목록 중 선택 → 추출. 이 흐름은 개별 객체 자료 확보 후 활성화한다.

**AI 이용:** 자연어 요청 → `geo_link_*` 호출 → 대화 안 결과 미리보기·옵션 변경 → 결과 파일. 화면 미지원 호스트에는 텍스트 요약과 웹 연결을 제공한다.

## 4. 개발 범위와 기능 공개 조건

### 4.1 A단계: 이번 개발에서 완결할 범위

PNU 분해·조합, 법정구역 코드·명칭 조회, 지번주소의 제한된 구조 파싱, 단계별 출력, CSV·XLSX 일괄 처리, 결과 표·복사·다운로드, 기준 자료 버전·갱신 확인, 웹·MCP·MCP Apps의 공통 실행을 구현한다.

실제 법정구역 사전으로 코드와 명칭을 대응시킨다. 인증·원천 접근이 막히면 파서·테스트·화면은 계속 구현하되, 시험용 사전을 운영 전국 자료인 것처럼 표시하지 않는다. 이 경우 ‘기술 구현 완료’와 ‘실데이터 운영 준비 미완료’를 구분해 보고한다.

### 4.2 B단계: 자료가 검증된 기능부터 확장

행정동 대응, 도로명주소·지번 관계, 우편번호, 지역 내 주소·객체 목록, 좌표 변환·위치 확인, Point·Line·Polygon 검색, 공개 토지·건물 속성, GeoJSON·GeoPackage·SHP 추출을 확장한다.

다섯 입력을 최종 기능 방향에서 삭제하지 않는다. 다만 미확보 자료에 기대는 빈 버튼과 가짜 결과를 초기 완료 기능으로 만들지 않는다. 화면에는 실제 이용 가능한 기능과 준비 상태를 구분한다.

### 4.3 제공 상태 계약

기능별 상태를 `available / setup_required / source_unavailable / planned`로 관리한다. 각 상태에는 지역 범위, 데이터셋, 기준 버전, 지원 작업, 제한 사유가 붙는다.

지원 범위는 ‘전국 가능’ 같은 문장 하나가 아니라 데이터셋별로 정한다. 코드 사전의 전국 지원과 전국 필지·건물 목록의 확보는 별개다. 건물 주소 DB로 건물이 없는 모든 토지의 주소를 확보했다고 처리하지 않는다. [S04]

## 5. 국내 코드·주소 도메인 규칙

### 5.1 코드 체계와 출력 표현

입력·결과에는 코드값뿐 아니라 `codeSystem`을 보존한다. 초기는 `pnu`, `legal_region`을 중심으로 하고, 이후 `administrative_region`, `postal` 등 지원 체계를 추가한다. 서로 다른 기관의 코드를 같은 자리수라는 이유로 같은 체계로 취급하지 않는다.

법정구역의 구성은 시도 2자리 + 시군구 3자리 + 읍면동 3자리 + 리 2자리다. 누적 접두 코드는 2·5·8·10자리로 추출한다. 공식 지역코드 조회는 사전에 등록된 코드와 상위 관계를 이용한다. [S01][S02]

출력은 다음 세 가지를 구분한다.

- **접두 코드:** PNU 등에서 앞 2·5·8·10자리를 추출한 값.
- **사전 등록 전체 코드:** 선택한 구역에 실제로 등록된 전체 코드. 단순 0 채우기 결과를 사전 확인 없이 공식 코드로 확정하지 않는다.
- **사용자 지정 문자열 추출:** 앞 N자리 등 임의 범위. 공식 행정구역 코드라는 이름을 붙이지 않는다.

코드 표현과 주소 표현은 독립적이다. 예를 들어 코드 8자리와 전체 지역명 경로를 함께 출력하거나, 최하위 명칭만 출력할 수 있다. 항목별 분리는 시도명·시군구명·읍면동명·리명·일반/산·본번·부번 등의 열을 제공한다.

### 5.2 계층과 국내 예외

상위·하위 관계는 원천 사전으로 해석한다. 시 아래 일반구가 있으면 시 전체 선택 시 하위 구를 포함한다. 같은 5자리 접두어를 갖는 객체만 찾는 방식으로 시 전체를 정의하지 않는다.

사용자에게 보이는 시군구명은 필요하면 ‘시 + 구’를 함께 표현한다. 리가 없으면 빈 리 명칭을 만들지 않는다. 코드상 구성요소와 화면의 주소 단계가 반드시 일대일이라는 전제를 두지 않는다.

PNU는 법정구역 기준이다. 행정동을 얻으려면 관할 관계 자료 또는 검증된 개별 주소 관계가 필요하다. 법정동 하나에 대응하는 행정동 후보가 여럿이면 그것만으로 개별 필지의 행정동을 하나로 확정하지 않는다. 추가 주소 단서·공간 관계가 없으면 후보 상태로 둔다. [S03]

### 5.3 현재·과거 코드

기본 조회는 활성 기준 자료를 사용한다. 말소·폐지 코드는 별도 상태로 보존한다. 과거 명칭을 현재 명칭으로 치환하거나 과거 PNU를 새 PNU로 바꾸는 작업은 단순 명칭 변경과 구분한다.

유효기간과 선후행 관계가 확보된 경우에만 이력 정보를 보여준다. 과거 전 시점 복원은 초기 필수 기능이 아니다. 실행 결과에는 사용한 사전 버전을 고정해서 기록한다.

## 6. 내부 변환 로직

### 6.1 공통 입력 처리

원본을 먼저 보존하고 논리적인 입력 행 ID를 부여한다. 문자열 앞뒤 공백과 BOM 등 허용된 정제만 별도 정규화값에 적용한다. 원본 문자열 자체를 덮어쓰지 않는다.

숫자 셀·지수 표기·손상된 식별자·날짜로 읽힌 값은 별도로 검사한다. 특히 긴 코드의 손실을 근거 없이 추정 복구하지 않는다. 쉼표·문자를 무작정 지워 19자리로 맞추는 로직은 금지한다.

입력 자동 판별은 후보 제안이다. 5자리 값은 시군구 접두 코드와 우편번호 후보를 구분해야 하고, 10자리 값도 코드 체계가 모호할 수 있다. 사용자 지정 유형, 해당 데이터셋의 컬럼 정의, 실제 사전 조회를 함께 사용한다. 둘 이상 가능하면 선택을 요청한다.

### 6.2 PNU → 지번 표현·부분 코드

```text
1. 원본 문자열과 행 ID를 보존한다.
2. 허용된 정제 후 19자리 ASCII 숫자인지 확인한다.
3. 아래 구간으로 분리한다. 인덱스는 0부터 시작한다.
   legalCode = pnu.slice(0, 10)
   landFlag  = pnu.slice(10, 11)
   mainNo    = pnu.slice(11, 15)
   subNo     = pnu.slice(15, 19)
4. core PNU 규약의 일반(1)·산(2) 구분을 검사한다.
5. 법정구역 사전에서 legalCode, 명칭 경로, 상태, 기준 버전을 조회한다.
6. 주소 표현용 본번·부번에서만 선행 0을 제거한다.
   부번 0000은 '-0'을 붙이지 않는다. 산은 별도 접두 표시한다.
7. 사용자가 선택한 단계·코드 형태·열에 맞추어 결과를 투영한다.
8. 코드 사전 확인과 개별 필지 존재 확인을 별도 기록한다.
```

PNU 구조의 근거는 [S01], 원천별 일반·산 코드 차이를 주의해야 하는 근거는 [S04][S07]이다. 외부 자료의 산여부가 `0/1`인 경우는 어댑터에서 `1/2` core 표현으로 명시적으로 변환한다. 블록·가번·기타 값을 무조건 일반으로 바꾸지 않는다.

**형식 설명 예시:** `1111010100 + 1 + 0001 + 0000`을 결합하면 `1111010100100010000`이다. 이 예시는 분해·조합 규칙을 보여주는 것이며, 이 번호의 현재 실재 필지를 이번 작업에서 확인했다는 뜻이 아니다.

유효한 형식이지만 사전에 없는 법정구역이라면 추출된 구성요소는 제공할 수 있어도 주소명을 만들어내지 않는다. `산`은 지번 구분이지 토지의 지목을 확인했다는 뜻이 아니다.

### 6.3 지번주소 → PNU 형식 조합

주소 끝의 지번 후보와 지역명 후보를 분리하되, 숫자가 들어 있는 동명과 건물 동·호를 지번으로 혼동하지 않는다. 원문, 소비한 구간, 남은 구간을 기록한다.

지역명은 사전의 전체 경로·명칭·명시적인 별칭으로 찾는다. 상위 지역이 부족한 같은 이름은 후보를 유지한다. 읍면동까지만 주어졌는데 리가 필요한 경우에는 임의의 리를 고르지 않는다.

법정구역 후보가 유일하고 일반·산, 본번·부번이 지원 범위 안에서 확정되면 각 4자리로 패딩해 PNU 형식값을 조합한다. 본번 0·블록·가번 등 일반 지번 범위를 벗어난 입력은 지원 규칙을 확인하거나 검토 상태로 남긴다. 문자열을 그럴듯하게 만드는 것을 우선하지 않는다.

동·호·건물명 등 아직 해석하지 못한 정보가 남으면 경고 또는 사용자 확인이 필요하다. 행정동명만 있는 주소를 법정동명으로 간주하거나, 도로명주소의 건물번호를 토지 본번·부번에 그대로 넣지 않는다.

결과의 기본 확인 수준은 ‘주소 구성과 코드 사전으로 생성’이다. 개별 필지 자료와 대조했을 때만 별도의 원천 확인 표시를 한다.

### 6.4 지역코드 ↔ 명칭

코드 체계를 먼저 결정하고 코드·상태·유효기간을 조회한다. 접두 코드 입력이면 해당 단계의 후보를 찾고, 요청한 상위 경로와 하위 지역을 반환한다.

코드 목록 조회와 하위 토지·건물 주소 조회는 다른 작업이다. 후자는 별도 객체 자료의 coverage를 확인한 뒤 실행한다. ‘지역명 한 건’과 ‘지역 내 개별 주소 목록’을 같은 성공 응답으로 혼동하지 않는다.

### 6.5 도로명주소·우편번호·건물 연계

도로명주소↔지번주소는 확보한 관계 자료를 통해 연결한다. 산술적으로 서로 바뀐다고 가정하지 않는다. 대표지번과 관련지번을 구분하고, 하나의 주소에 여러 필지·건물이 연결되면 관계별로 보존한다. 주소기반산업지원서비스의 건물 DB 안내도 건물과 관련 토지 정보를 구분한다. [S04]

건물관리번호는 제공되면 원천 식별자로 보존한다. 번호 앞부분을 잘라 현재 PNU로 간주하는 규칙은 사용하지 않는다. 건축물대장 기록도 건물 객체와 무조건 일대일로 취급하지 않는다.

우편번호는 별도 체계다. 번호에 대응하는 주소 목록과 공식 경계 자료의 확보는 구분한다. 주소점만 가지고 만든 범위를 공식 우편구역 경계라고 제공하지 않는다.

### 6.6 공간·좌표·비공간 속성에서 시작하는 확장 로직

**좌표:** 좌표값과 EPSG, 축 순서, 단위를 확인한다. 좌표계가 없는 X·Y는 추정값을 확정하지 않는다. 좌표 변환은 위치 표현 변경이고, 필지·건물 찾기는 공간 자료 조회다. 둘의 실패를 분리한다.

**Point:** 포함·경계 접촉과 주변 검색을 구분한다. 공유 경계 위의 점은 여러 후보를 반환할 수 있다. 가까운 건물을 해당 지점의 건물로 단정하지 않는다.

**Line:** 원천 객체 식별자가 있으면 도로·경계 자체의 정보를 우선 조회한다. 사용자가 그린 선은 검색 범위다. 통과·교차·설정 거리 이내 관계를 구분한다.

**Polygon:** 완전 포함·일부 교차·대표점 포함 중 선택한 규칙을 실행한다. 불량 도형을 보정하면 보정 사실과 원본을 남긴다. 잘라낸 도형의 계산 면적을 원천 전체 면적과 같은 필드로 덮어쓰지 않는다.

**비공간 속성:** 파일에 있는 주소·코드 등의 단서로 대상 연결을 시도한다. 면적·용도만 있는 자료는 단일 객체 식별이 아니라 조건 검색으로 처리한다. 구역 통계는 구역의 속성이지 개별 필지·건물의 속성이 아니다.

공간 계산 결과에는 관계 종류와 사용한 원천·기준일·좌표계를 남긴다. 대표점, 중심점, 출입구, 사용자 클릭 지점도 서로 구분한다.

## 7. 공통 결과 규격

### 7.1 행 단위 결과

아래는 내부 계약의 기본안이다. DB 스키마가 아니라 웹·MCP·파일 출력이 공통으로 이용하는 결과 구조다.

```ts
type LinkStatus = 'ok' | 'needs_selection' | 'invalid' | 'not_found' | 'unavailable'

type LinkRow = {
  inputId: string
  sourceRowIndex: number
  original: Record<string, string | null>
  normalized: Record<string, string | null>
  status: LinkStatus
  values: Record<string, string | number | null>
  candidates: Array<{
    candidateId: string
    codeSystem: string
    code: string
    label: string
    method: string
    sourceRef: string
  }>
  verification: {
    syntax: 'valid' | 'invalid' | 'not_applicable'
    code: 'active' | 'retired' | 'unknown' | 'not_checked'
    parcel: 'matched' | 'no_match_in_dataset' | 'not_checked'
  }
  issues: Array<{ code: string; message: string; field?: string }>
  provenance: Array<{ sourceId: string; version: string; recordId?: string }>
}
```

`values`의 일반 수치에는 숫자를 쓸 수 있으나 PNU·지역코드·우편번호 등 식별 필드는 반드시 문자열이다. 실제 구현에서는 필드별 타입·스키마 검증으로 강제한다.

`not_found`는 조회가 정상 완료된 지원 자료에서 대응 기록을 못 찾았다는 뜻이다. 원천 미수집·장애·권한 부족은 `unavailable`과 세부 사유로 구분한다. `no_match_in_dataset`도 현실에서 해당 필지가 없다는 확정이 아니다.

필수 오류·경고 코드는 `INVALID_LENGTH`, `INVALID_LAND_FLAG`, `CODE_UNKNOWN`, `CODE_RETIRED`, `AMBIGUOUS_REGION`, `UNPARSED_ADDRESS_PART`, `IDENTIFIER_PRECISION_LOSS`, `SOURCE_NOT_READY`, `OUT_OF_COVERAGE`, `UNSUPPORTED_ADDRESS_TYPE` 등을 정의한다. 사용자 문구와 프로그램용 코드를 분리한다.

### 7.2 실행 단위 메타데이터

실행마다 스키마 버전, 규칙 버전, 기준 자료 버전 목록, 입력 체크섬, 정규화한 옵션, 시작·종료 시각, 행 수와 상태별 집계, 제한·경고를 저장한다.

작업 시작 시 기준 자료 버전을 고정한다. 처리 중 사전이 갱신되어도 같은 파일의 앞·뒤 행이 서로 다른 버전을 쓰지 않는다.

웹·MCP 동등성 테스트는 행의 결과·상태·후보·사전 버전을 비교한다. 작업 UUID·실행 시각·소요 시간까지 동일해야 한다는 의미는 아니다.

### 7.3 다대다 관계와 출력

기본 결과는 입력 한 행을 유지하고 후보를 별도 배열·목록으로 연결한다. 사용자가 명시적으로 행 펼치기를 선택한 경우만 후보별 행을 만든다. 이때 `inputId`, `matchId`, 대상 종류와 매칭 근거를 포함한다.

객체 목록과 주소 문자열 중복 제거 목록은 별도 모드다. 주소가 같다는 이유만으로 필지·건물 객체를 삭제하지 않는다. 면적 등의 집계는 실제 객체 ID 기준으로 하고 관계로 늘어난 행 수를 객체 수로 계산하지 않는다.

## 8. 내부 구조와 파일 배치 제안

```text
app/pages/link/                    신규 작업·지역 탐색·자료 현황 화면
app/components/link/               입력 옵션·결과 표·후보 선택 UI
shared/link/                       도메인 타입·스키마·PNU 규칙·정제·출력 규칙
server/services/link/              공통 실행·사전 조회·원천 어댑터·파일 처리
server/api/link/                   웹용 얇은 HTTP 어댑터
server/mcp/link.ts                 MCP 도구 등록(제안 위치)
server/assets/mcp-link.html         연계용 MCP Apps UI
scripts/link/                      기준 자료 수집·검증·활성화·배치 작업
tests/link/                       단위·계약·오류·일괄 처리 테스트
.data/reference/link/              원천 사전·검증된 버전·현재 버전 포인터
.data/link/stage/                   연계 입력 임시 파일
.data/link/jobs/                    연계 작업·미리보기·결과·보고서
```

위 트리의 경로는 신규 제안이다. 현재 리포지토리 구조가 작업 시점에 달라졌으면 역할에 맞춰 위치를 조정하고 문서를 갱신한다.

순수 규칙은 파일 접근·Nitro 전역·외부 API에 의존하지 않게 만든다. 도메인 함수는 같은 snapshot과 options를 주면 같은 결과를 반환해야 한다.

웹 API와 MCP는 요청 검증·권한 확인·응답 표현만 담당하고 동일한 `resolveLink`·`startLinkJob` 등 공통 서비스에 위임한다. 브라우저에만 있는 주소 변환과 MCP 서버에만 있는 변환을 따로 만들지 않는다.

작은 코드 사전은 버전 파일과 메모리 조회 인덱스로 시작할 수 있다. 규모·검색 요구가 커지면 SQLite 또는 기존 PostGIS 인프라를 검토한다. 첫 변환을 위해 전국 폴리곤 DB가 준비될 때까지 기다리지 않는다.

## 9. HTTP·MCP 인터페이스 제안

### 9.1 공통 요청 예시

```json
{
  "operation": "convert",
  "input": {
    "kind": "values",
    "valueType": "pnu",
    "values": ["1111010100100010000"]
  },
  "regionBasis": "legal",
  "projection": {
    "level": "emd",
    "codeForm": "prefix",
    "addressForm": "full_path",
    "columns": ["input", "region_code", "region_name", "status"]
  },
  "preserveRows": true,
  "referenceVersion": "current"
}
```

예시는 형식 설명용이다. 실제 요청에서 `current`는 실행 시작 시 구체적인 활성 버전으로 해석하고 응답에 그 버전을 적는다. 지원하지 않는 체계·작업·열은 무시하지 말고 검증 오류를 반환한다.

### 9.2 HTTP 엔드포인트

| 제안 경로 | 역할 |
|---|---|
| `GET /api/link/capabilities` | 지원 기능·원천·지역·버전·한도·준비 상태 |
| `POST /api/link/resolve` | 제한된 소량 입력의 동기 변환 |
| `GET /api/link/regions` | 체계·코드·명칭·상위 지역 조건으로 후보 조회 |
| `POST /api/link/stage` | 파일 수신·문자열 보존·컬럼 미리보기 |
| `POST /api/link/jobs` | 확인한 입력·매핑·옵션으로 일괄 작업 생성 |
| `GET /api/link/jobs/:id` | 작업 상태·집계·메타데이터 |
| `GET /api/link/jobs/:id/rows` | 페이지 단위 결과·오류·후보 조회 |
| `POST /api/link/jobs/:id/export` | 선택 열·모드·형식의 결과 파일 생성 |
| `GET /api/link/jobs/:id/artifacts/:artifactId` | 권한·만료 확인 후 파일 전달 |

큰 파일 작업은 작업 ID를 반환하고 상태를 조회한다. 결과 수가 많다고 임의로 앞부분만 반환하면서 ‘전체 완료’라고 하지 않는다. `total`, `returned`, `nextCursor`, `truncated` 등의 의미를 명확히 한다.

조회만 하는 GET에 작업 실행·새 파일 생성 부작용을 넣지 않는다. 파일 생성·작업 시작은 입력 체크섬·옵션·기준 버전·사용자 범위에 묶인 멱등 키로 중복 실행을 제어한다.

### 9.3 MCP 도구

기존 도구명·입력 스키마·기능을 보존한다. 신규 기본 도구는 다음과 같이 제안한다.

| 도구 | 동작 |
|---|---|
| `geo_link_capabilities` | 실제 지원 범위와 데이터 상태를 확인 |
| `geo_link_resolve` | 소량 변환. 입력이 없으면 지원 호스트에서 연계 입력 화면 제공 |
| `geo_link_regions` | 지역코드·명칭·하위 지역 후보 조회 |
| `geo_link_run` | 맡긴 파일 또는 검증된 입력으로 일괄 작업 시작 |
| `geo_link_status` | 진행·집계·오류 요약·웹 결과 주소 조회 |
| `geo_link_export` | 결과 열·형식을 선택하여 파일 생성·안내 |

앱의 페이지 조회·업로드 조각 전달 등은 필요하면 앱 전용 도구로 분리한다. 모델이 볼 도구를 과도하게 늘리지 않는다. 새 연계 작업을 기존 `geo_status`가 처리한다고 가정하지 않는다.

도구 설명은 ‘무엇을 주면 무엇을 반환하는지’와 미지원 범위를 명확히 한다. 조회 도구와 파일 생성 도구의 부작용 속성도 실제 동작에 맞게 선언한다. 프로토콜 도구의 입력·출력 스키마와 오류 표현을 준수한다. [S06]

### 9.4 MCP Apps UI

같은 `/mcp`에서 기존 `ui://geo/app.html`을 유지하고, 제안 리소스 `ui://geo/link.html`에 `mcp-link.html`을 연결한다. UI 리소스는 연결된 도구에서 명시적으로 참조한다. [R07][S05]

앱에는 유형·단계·열 선택, 후보 확인, 제한된 결과 미리보기, 진행 상태, 다운로드·웹 열기를 제공한다. 고급 지도·큰 속성표는 웹 화면으로 이어서 볼 수 있다.

호스트의 UI·다운로드·링크 열기 지원을 감지한다. 미지원이면 텍스트 요약과 웹 이용 경로를 안내한다. 특정 호스트의 로컬 링크 제한을 모든 MCP 환경의 규칙으로 일반화하지 않는다.

현재 프로젝트는 설치된 SDK의 앱 번들을 서버에서 삽입한다. 우선 이 패턴을 검토·재사용하고, 최신 공식 샘플의 버전이 다르다는 이유만으로 SDK와 전체 빌드 체계를 일괄 교체하지 않는다. [R03][R07][R08]

`content`와 `structuredContent`를 원본 파일 전체의 보관 장소로 사용하지 않는다. AI에 반환할 요약·미리보기·파일 참조를 제한하고, 화면용 데이터가 무조건 모델에 숨겨진다고 가정하지 않는다. 민감자료는 호스트 전달 경로까지 확인한 후 사용한다.

## 10. 파일 처리·출력·시각화 연결

### 10.1 CSV·XLSX 입력

CSV는 구분자·인용부호·개행·문자 인코딩을 검사하고 미리보기를 제공한다. UTF-8을 기본으로 하되 국내 업무 파일에서 다른 인코딩을 선택할 수 있게 한다. 판별이 불확실하면 사용자 확인을 받는다.

XLSX는 시트·헤더 행·컬럼을 선택한다. 식별자 열은 문자형을 보존한다. 숫자 셀로 저장된 긴 값의 정밀도 손실을 경고하고, 수식·매크로를 실행하지 않는다. 입력 파일의 외부 링크를 자동으로 따라가지 않는다.

서버·브라우저 파서의 값 해석이 다르지 않도록 테스트한다. 원본의 셀 값과 정규화 값, 원본 행 번호를 보존한다. 빈 행·중복 행을 자동 제거하지 않고 선택 사항으로 둔다.

### 10.2 다운로드

A단계는 CSV·XLSX·JSON을 지원 대상으로 한다. XLSX의 코드 셀은 명시적인 문자형으로 출력한다. CSV를 따옴표로 감쌌다는 이유만으로 엑셀의 자동 숫자 해석을 막았다고 주장하지 않는다. 엑셀 작업에서는 XLSX 또는 텍스트 가져오기 방식을 안내한다.

외부 입력이 `=`, `+`, `-`, `@` 등으로 시작하는 경우 스프레드시트 수식 실행을 유발하지 않도록 형식별 안전 처리를 한다. 안전 처리한 열은 설명에 기록하고 내부 원본 값은 별도로 보존한다. 코드 보존과 수식 방지는 서로 다른 검증 항목이다.

복수 후보는 기본 결과와 별도 후보 목록으로 내보내고, 펼친 출력에는 입력 ID·후보 ID를 넣는다. 파일에는 출처, 기준 버전, 선택 옵션, 상태별 건수, 미확인 범위를 포함한 메타정보를 제공한다.

공간 출력은 B단계다. RFC 7946 GeoJSON은 WGS84 경도·위도 순서로 출력한다. 다른 투영좌표 출력은 적절한 별도 형식으로 제공한다. 위치를 확인하지 못한 행에 가짜 좌표를 넣지 않는다. [S08]

### 10.3 기존 시각화 도구와 연결

A단계에서는 ‘지도가 아직 없는 결과’를 정상으로 취급한다. 실제 좌표·도형이 확보되었을 때만 지도 미리보기와 시각화로 보내기를 활성화한다.

기존 `/viz/upload`는 브라우저 파일을 판별해 `/api/jobs`로 보내는 흐름이다. 현재 코드 검토 범위에서는 `?stage=`로 파일을 자동 가져오는 흐름이 확인되지 않았다. 따라서 단순히 그 URL만 만드는 것으로 연계 완료라고 하지 않는다. [R09]

최소 구현은 결과 GeoJSON 다운로드 후 기존 업로드로 연결하는 방식이다. 직접 연결을 구현할 때는 서버가 권한을 확인하고 결과 파일을 기존 stage로 안전하게 복사한 뒤, `/viz/upload`에 명시적인 stage 불러오기 지원을 추가한다. 임의 서버 경로·외부 URL을 브라우저에서 전달받아 그대로 읽지 않는다.

원본 연계 작업과 후속 시각화 작업의 관계를 기록한다. 후속 작업이 원본 만료에 영향을 받는지, 파일이 독립 복사되었는지도 명시한다. 기존 뷰어를 재사용하되 지원하지 않는 `OutputKind`를 임의로 추가하지 않는다.

## 11. 원천 자료 확보와 갱신

### 11.1 우선 원천

A단계의 첫 원천은 행정안전부 법정동코드 자료다. 공개 API는 현재 제공 중인 법정동 코드의 조회 경로로 안내되어 있다. 전체 수집 가능 범위·호출량·폐지 코드 포함 여부·상위 관계 필드는 실제 응답과 제공 문서로 검증한다. [S02]

행정동 대응은 행정안전부의 행정기관·법정동·관할 관계 자료를 별도로 검토한다. 안내 게시물 하나를 전국의 최신 기준본이라고 고정하지 않는다. [S03]

주소·건물·우편번호는 주소기반산업지원서비스의 자료를 검토한다. 필지 목록, 공간도형, 토지·건물 속성은 별도 공급원과 이용 조건을 확인한다. [S04]

각 데이터셋에 sourceId, 제공기관, 원문 경로, 제공 형태, 신청·인증 조건, 이용·가공·재배포 조건, 지역 범위, 필드 명세, 기준일, 수집일, 유효기간, 판별·연계 키를 기록한다.

### 11.2 스냅샷 구조

```text
.data/reference/link/<sourceId>/
  versions/<versionId>/
    raw/                 허용된 범위의 원본
    normalized/          정규화 자료·조회 인덱스
    manifest.json        기준일·수집일·체크섬·행 수·라이선스·검증 결과
  active.json            현재 공개 버전 참조
```

이 구조는 구현 기본안이며 DB 테이블을 고정하는 명세가 아니다. 여러 원천을 함께 쓸 때는 실행에서 각 원천의 버전을 고정한다. 기준일이 다른 자료를 임의로 같은 날짜로 표시하지 않는다.

### 11.3 일일 확인 절차

원천별 마지막 성공 상태를 읽고 새 배포본·변경분·조건부 응답을 확인한다. 새 자료가 있으면 별도 위치에 수집하고 형식, 코드 중복, 부모 관계, 순환 참조, 삭제·폐지량, 필수 열을 검사한다.

검증 성공 후 활성 버전을 원자적으로 교체한다. 실패하면 기존 정상 버전을 계속 제공하고 오류를 남긴다. 일별 증분을 제공하는 자료는 누락 기간을 이어받고 같은 파일의 재적용이 안전하도록 처리한다. 전체 스냅샷 자료에 임의의 ‘일일 CDC’를 만들어 약속하지 않는다.

법정구역·주소·대장·도형의 변경은 각각 확인한다. 주소가 바뀐 객체만 조회하는 것으로 모든 속성 변경을 포착했다고 보지 않는다. 한 원천 기록의 삭제를 연결된 다른 객체의 삭제로 전파하지 않는다.

### 11.4 시각·운영 표시

`sourceAsOf`, `publishedAt`, `checkedAt`, `ingestedAt`, `effectiveFrom/To`를 확보 가능한 범위에서 구분한다. 원천이 기준일을 제공하지 않으면 수집일을 기준일로 위장하지 말고 ‘기준일 미제공’이라고 표시한다.

실행 결과는 `updated / no_change / failed / setup_required` 등으로 기록한다. 운영자가 매일 확인했다는 표시와 원천이 매일 갱신된다는 표현을 구분한다.

초기 실행 도구는 기존 서버 운영 환경의 스케줄러로 충분하다. 스케줄 설치는 배포 권한 안에서 수행하고, 로컬 문서 작성만으로 운영 자동화가 활성화되었다고 보고하지 않는다.

## 12. 작업 실행·한도·안전

### 12.1 작업 생명주기

소량 순수 변환은 동기로 처리하고, 파일·외부 조회·공간 처리·큰 출력은 별도 작업으로 수행한다. 신규 작업 상태는 `queued → running → completed / completed_with_issues / failed / cancelled`를 기본안으로 한다.

처리 중단·재시작 후 영원히 running으로 남지 않게 한다. 최초에는 중단된 작업을 실패로 표시하고 같은 입력·옵션으로 재실행하는 방식도 허용한다. 부분 재개를 구현했다면 재처리 범위와 중복 방지 테스트까지 한다.

초기 한도 제안은 소량 입력 200행, 파일 20MB·50,000행, 화면 미리보기 50행, 모델 반환 미리보기 10행이다. 이는 측정 전의 **보수적인 시작 설정**이지 보장 처리량이 아니다. 기존 시각화 파일의 200MB 한도를 새 표 파일에 자동 적용하지 않는다. [R05]

### 12.2 만료와 정리

새 임시 파일·결과의 기본 보관안은 24시간이며 설정 가능하게 한다. 읽기 API도 expiresAt을 검사하고, 물리적 삭제는 정기 정리 작업으로 수행한다. ‘24시간 뒤 접근 불가’와 ‘실제 디스크 삭제 완료 시각’을 구분한다.

기존 시각화 작업 정리는 새 작업 시작에 연결되어 있으므로, 그 동작을 매 시각 자동 삭제라고 문서화하지 않는다. 새 참조자료는 어떤 임시 정리 대상에도 포함하지 않는다. [R05][R06]

### 12.3 접근·파일·외부 통신

작업 소유자 또는 적절한 접근권한을 검증한다. 회원가입 없이 제공하더라도 비공개 세션·권한 토큰 등 명시적인 설계가 필요하다. MCP 요청에서 사용할 권한 정보도 호스트와 배포 방식에 맞춰 검증한다. UUID만 아는 다른 사용자가 원본·전체 결과를 조회할 수 있어서는 안 된다.

외부 서비스 인증키는 서버에만 둔다. 민감한 원문·파일·인증키를 로그나 모델 응답에 남기지 않는다. UI에는 외부 텍스트를 안전하게 렌더링한다. ZIP 기반 파일에는 압축 해제 크기·파일 수·경로 이동 제한을 적용한다.

로컬 파일 읽기는 신뢰된 로컬 환경에서 명시적으로 허용할 때만 제공한다. 외부 공개에서는 기본 차단한다. forwarded host 값만으로 로컬 권한을 부여하지 않는다.

사용자 입력을 셸 명령·SQL·임의 URL 요청으로 직접 연결하지 않는다. API 호출은 허용한 원천 어댑터와 제한된 매개변수로만 실행한다. AI가 보낸 자유 텍스트를 실행 명령으로 취급하지 않는다.

### 12.4 성능 측정

단건 분해·사전 조회, 주소 파싱, 파일 변환, 공간 검색, 파일 생성 시간을 구분한다. 데이터 버전·행 수·실행 환경·동시성·오류율과 함께 측정한다. ‘모든 결과 100ms’, ‘전국 DB 60~80GB’ 같은 검증되지 않은 값을 성공 조건으로 사용하지 않는다.

기존 `npm run check`는 실행 산출물에 의존한다. 원본·report.json이 없는 환경에서는 기존 실패와 이번 변경으로 생긴 실패를 구분한다. 이 검사를 삭제하거나 무조건 성공하도록 바꾸지 않는다. 새 `test:link` 등 독립적인 테스트 명령과 `npm run build`를 함께 검증한다. [R10]

## 14. 구현 순서와 변경 관리

**첫 묶음 — 도메인과 자료:** 기준 자료 명세·loader, 순수 PNU 규칙, 법정구역 조회, 결과·오류 계약, 단위 테스트를 만든다.

**둘째 묶음 — 실제 웹 작업:** `/link`, 목록·파일 입력, 컬럼·출력 선택, 결과 검토·CSV/XLSX 출력, 작업 상태를 연결한다.

**셋째 묶음 — AI 이용:** 기존 `/mcp`에 새 도구·UI를 추가하고 웹과 결과 동등성을 검증한다. UI 없는 호출도 완성한다.

**넷째 묶음 — 운영·회귀:** 기준 자료 갱신·실패 복구·만료·접근 제한을 검증하고 소개·AI 안내·README를 갱신한다.

**다음 확장 — 원천 기반 연결:** 검증된 행정동·도로명·우편번호·개별 객체·공간·속성 어댑터를 추가한다. 다섯 입력의 최종 구조는 유지하되 데이터 미확보를 이유로 A단계 전체를 미루지 않는다.

구현에 필요한 작은 판단은 개발자가 근거를 기록하고 진행한다. DB나 수집 방식이 바뀌어도 사용자 결과의 의미·원본 보존·검증 기준은 유지한다. 외부 유료 사용, 공개 배포, 권한 확대, 파괴적 데이터 변경은 별도 승인 범위로 둔다.
