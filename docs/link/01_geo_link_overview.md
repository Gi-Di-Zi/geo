## 1. 왜 만드는가

출발점은 회사에서 사용하는 **PNU와 주소를 서로 바꾸는 프로그램**이었다. 숫자로 된 토지 식별번호를 사람이 읽을 수 있는 주소로 바꾸는 일이 실제 업무에 필요했고, 일일이 확인하고 가공하는 과정에 불편함이 있었다.

비슷한 작업은 PNU에만 한정되지 않는다. 시군구 코드만 있는 자료에서 지역명을 붙이거나, PNU에서 읍면동 코드까지만 잘라 쓰거나, 특정 지역에 있는 토지·건물 주소 목록을 가져오는 작업도 필요하다.

이 프로젝트는 이런 반복 작업을 한곳에서 처리하도록 만드는 것이다. 처음부터 거대한 부동산 정보 사이트를 만드는 것이 아니라, **가지고 있는 자료를 원하는 형태로 바꾸어 바로 업무에 가져가는 것**을 우선한다.

이 배경과 요구는 사용자가 설명한 실제 업무 경험에 근거한다. 아래 화면 구성과 개발 순서는 그 요구를 구체화한 제안이다.

## 2. 어떤 일을 할 수 있는가

### 숫자로 된 코드를 읽을 수 있는 이름으로 바꾸기

PNU나 지역코드를 입력하면 주소와 지역명을 확인한다. 반대로 지번주소에 해당하는 PNU 형식의 값을 만들거나, 지역명으로 코드를 찾는다.

PNU는 토지를 식별하는 19자리 코드다. 앞부분에는 법정구역 코드가, 뒤에는 일반·산 구분과 지번의 본번·부번이 담겨 있다. **PNU의 구성을 해석하는 것과 해당 필지가 실제 자료에 존재하는지 확인하는 것은 서로 다른 작업**으로 안내한다. [S01]

### 필요한 부분만 꺼내기

사용자가 다음 두 가지를 각각 선택한다.

**어디까지 필요한가:** 시도 / 시군구 / 읍면동 / 동·리 / 지번 / 전체 PNU.

**어떤 모습으로 필요한가:** 코드만 / 이름만 / 코드와 이름 / 항목을 열별로 분리.

예를 들어 PNU 500개에서 시군구 코드만 꺼내거나, 지역코드 목록에 시도명·시군구명·읍면동명을 각각 붙이는 작업을 할 수 있게 한다. 500개는 사용 예시이며 처리 성능을 보장하는 수치가 아니다.

### 특정 지역의 주소 목록 가져오기

시군구나 읍면동을 선택한 뒤, 그 안에 있는 토지 또는 건물의 주소 목록을 조회한다. 결과에는 필요한 코드·주소·속성을 선택해서 포함한다.

이 기능은 코드 하나를 지역명 하나로 바꾸는 기능과 구분한다. 개별 토지·건물 자료가 확보되어야 제공할 수 있고, **지원 자료 안에서 확인되는 목록**이라는 범위를 표시한다. 건물 주소 자료만으로 건물이 없는 토지까지 전부 조회했다고 표시하지 않는다.

### 위치·지도·공공정보 연결하기

주소나 코드에 연결되는 좌표·도형·토지정보·건물정보를 확보한 범위에서 함께 보여준다. 반대로 좌표, 지도에서 선택한 범위, 공간 파일, 속성 조건에서도 검색을 시작할 수 있도록 확장한다.

최종적으로 유지할 다섯 출발점은 다음과 같다.

| 출발점 | 예시 | 연결해서 확인할 내용 |
|---|---|---|
| 주소·지명 | 지번주소, 도로명주소, 도로명, 장소명 | 코드, 좌표, 도형, 관련 속성 |
| 코드 | PNU, 법정동·행정동 코드, 우편번호 | 주소·지역명, 대응 코드, 관련 객체 |
| 공간데이터 | 점, 도로·경계선, 건물·필지·영역 | 관련 주소·코드·속성·좌표 |
| 비공간정보 | 토지·건물 속성 자료, 조건 검색 | 대응 대상의 주소·코드·도형·위치 |
| 위치 | 위경도, X·Y와 좌표계 | 그 위치에 대응하거나 주변에 있는 정보 |

이 표는 **전체 발전 방향**이다. 첫 버전에서 모든 자료가 이미 연결된다는 의미는 아니다.

## 3. geo에는 어떻게 들어가는가

현재 geo에는 실제 공간데이터를 처리하고 지도에서 확인하는 **공간 데이터 시각화 도구**가 있다. 최신 코드는 이 도구를 `/viz` 아래에 두고, 사이트 첫 화면과 프로젝트 목록을 분리했다. 프로젝트 목록에는 다음 프로젝트를 넣을 자리도 마련되어 있다. [R01][R02]

새 기능은 기존 도구를 덮어쓰지 않고, 같은 사이트의 두 번째 도구로 추가한다.

| 구역 | 역할 |
|---|---|
| 사이트 소개 `/` | geo에서 할 수 있는 일과 두 도구를 소개 |
| 시각화 도구 `/viz` | 기존의 파일 처리·형식 변환·지도·3D 결과 확인 |
| 주소·코드 연계 도구 `/link` | 주소·코드 변환, 단계별 추출, 관련 정보 연결 |
| AI 연결 안내 `/ai` | 두 도구를 AI에서 사용하는 연결 방법 안내 |

`/link`는 이번 문서에서 제안하는 새 경로다. 현재 구현된 경로라고 주장하지 않는다.

두 도구는 필요할 때 연결한다. 예를 들어 주소 목록에서 실제 좌표나 도형을 얻었다면 시각화 도구로 보내 지도에서 확인할 수 있게 한다. **코드만 변환한 결과에 위치정보가 없다면 지도에 임의로 점을 찍지 않는다.**

## 4. 이용 방법은 두 가지다

### 웹에서 직접 사용

사용자는 목록을 붙여넣거나 파일을 올리고, 결과에 필요한 항목을 고른다. 결과 표에서 오류를 확인한 뒤 복사하거나 파일로 받는다.

기본 흐름은 다음과 같다.

> **자료 넣기 → 필요한 결과 선택 → 변환 → 결과와 오류 확인 → 복사·파일 저장**

단순 코드 변환을 하는 사람에게 지도부터 띄우거나 복잡한 설정을 요구하지 않는다. 지도는 위치를 확인할 필요가 있을 때 사용한다.

### AI에 연결해서 사용

사용자가 AI에게 다음처럼 요청할 수 있게 한다.

> “이 파일의 PNU에서 읍면동 코드와 지역명을 뽑아줘. 원본 순서는 그대로 두고, 변환하지 못한 행도 남겨줘.”

AI는 요청에 맞는 옵션을 선택하고 geo의 도구를 호출한다. **주소·코드를 AI가 추측해서 계산하는 것이 아니라, 웹에서도 사용하는 동일한 변환 기능이 결과를 만든다.**

화면을 지원하는 AI에서는 대화 안에서 옵션과 결과 표를 조작할 수 있게 한다. 이것이 MCP Apps 방식이다. 화면을 지원하지 않는 환경에서도 기본 도구 호출과 결과 파일 안내는 사용할 수 있도록 한다. MCP Apps는 일반 MCP 도구에 대화형 화면을 더하는 확장이고, 호스트의 화면 지원 여부를 확인해야 한다. [S02]

현재 geo에도 MCP 도구와 대화 안 화면 코드가 있다. 이를 확장하되, 이번 검토에서는 실제 AI 클라이언트에서의 실행 시험까지 하지는 않았다. [R03]

## 5. 기본 화면은 어떻게 구성하는가

첫 화면에서는 **입력할 곳, 결과 옵션, 결과 표**가 먼저 보이게 한다.

입력 영역에서는 직접 입력·여러 줄 붙여넣기·파일 올리기를 선택한다. 무엇이 들어 있는지 자동으로 제안하되, 사용자가 PNU·지역코드·지번주소 등의 유형을 바꿀 수 있다.

결과 옵션에서는 출력 단계와 열을 고른다. 예를 들어 ‘읍면동까지’, ‘코드와 지역명’, ‘원본 열 유지’를 선택한다. 자주 사용하는 조합은 다시 쓸 수 있게 한다.

결과 표에는 원본 값과 변환 결과를 나란히 둔다. 정상 처리, 후보가 여러 개인 경우, 형식 오류, 원천 확인 불가를 구분한다. 실패한 행을 조용히 삭제하지 않는다.

상세 보기에서는 왜 이런 결과가 나왔는지, 어떤 기준 자료를 사용했는지, 마지막으로 언제 갱신했는지 확인한다. 일반 사용자는 상세 보기를 열지 않아도 기본 작업을 끝낼 수 있게 한다.

## 6. 국내 업무에 맞추어 지킬 기준

### 국내 지역 체계를 기본으로 한다

시도 → 시군구 → 읍면동 → 리를 사용자가 이해하는 기본 흐름으로 삼는다. 다만 시 아래에 구가 있거나 리가 없는 경우처럼 실제 자료의 단계가 달라도 자연스럽게 보여준다.

‘시 전체’를 고르면 그 아래 구를 포함한 범위를 조회하도록 한다. 특정 지역에만 맞춘 예외 코드를 늘리기보다 공식 자료의 상위·하위 관계를 따른다.

### 법정동과 행정동을 혼동하지 않는다

PNU에서 잘라낸 지역코드를 행정동코드라고 표시하지 않는다. 토지·주소를 위한 법정구역과 행정업무를 위한 구역은 구분하고, 서로의 관계는 별도 자료로 연결한다. 행정안전부도 법정동 코드, 행정동 코드, 관할 관계 자료를 구분해 제공한다. [S03]

### 코드의 원래 값을 지킨다

긴 숫자처럼 보이는 코드도 계산할 숫자가 아니라 식별 문자열로 취급한다. 앞자리 0이나 긴 PNU가 입력·다운로드 과정에서 달라지지 않도록 한다. 이미 원본 파일에서 숫자로 반올림되어 손상된 값은 임의로 복원하지 않는다.

### ‘변환’과 ‘확인’을 구분한다

주소 형식으로 바꾸었다고 해서 실제 필지의 존재까지 확인한 것은 아니다. 결과에는 ‘형식 변환’, ‘코드 사전 확인’, ‘개별 원천 자료 확인’을 구분해 표시한다.

코드 목록에서 이름을 찾지 못했을 때는 그 이유를 보여준다. 과거 코드, 아직 받지 않은 자료, 잘못된 입력을 모두 ‘없는 주소’로 단정하지 않는다.

## 7. 첫 개발에서 완성할 것

첫 개발 묶음은 **PNU·법정구역 코드·지번주소를 대상으로 하는 실제 업무 흐름 전체**다. 입력창만 만들거나 결과 모양만 보여주는 수준에서 끝내지 않는다.

| 필수 기능 | 첫 완료 기준 |
|---|---|
| PNU 분해와 형식 조합 | 구성요소와 오류를 확인하고 지번 표현을 만들 수 있음 |
| 법정구역 코드·지역명 조회 | 실제 기준 자료를 읽어 결과와 기준일을 제공함 |
| 단계·열 선택 | 코드 길이와 이름의 표시 범위를 각각 선택할 수 있음 |
| 목록·파일 처리 | 원본 행·순서를 유지하며 CSV·XLSX 입출력을 지원함 |
| 웹과 AI 연결 | 같은 자료·옵션·기준 자료에서 같은 의미의 결과를 제공함 |
| 결과 검증 | 정상·오류·복수 후보·원천 미확인 상태를 구분함 |
| 데이터 운영 | 기준 자료 수집·갱신 확인·실패 이력을 남김 |

XLSX는 엑셀에서 코드값을 보존하기 위한 초기 지원 대상으로 제안한다. 실제 라이브러리 선택과 파일 한도는 개발 과정에서 검증한다.

도로명주소, 행정동·우편번호 연계, 구역 안의 전체 주소 목록, 좌표·도형·공공 속성 연결은 그다음 확장 순서다. 필요한 원천과 이용 조건을 확인한 기능부터 제공하며, 아직 연결되지 않은 항목은 준비 상태와 이유를 표시한다.

## 8. 매일 갱신한다는 뜻

기본안은 **매일 새 자료가 나왔는지 확인하는 것**이다. 자료 제공기관이 월 단위로 갱신한다면 우리 서비스도 그 자료의 기준일을 월 단위로 표시해야 한다.

자료를 확인한 날과 실제 자료가 만들어진 기준일을 구분한다. 새 자료를 처리하다 실패하면 이전의 정상 자료로 서비스를 유지하고, 마지막 성공 시점과 실패 상태를 알려준다.

전국의 모든 필지·건물 데이터를 매일 새벽 통째로 받거나, 모든 원천이 일별 변경분을 준다고 전제하지 않는다. 실제 제공 방식에 맞추어 운영한다.

## 9. 하지 않는 것과 보호할 것

이 도구는 공식 대장 발급이나 법적 경계 확정, 부동산 가치 평가를 대신하지 않는다. 건물관리번호를 필수 입력으로 요구하지 않는다. 모든 정보를 100ms 안에 제공한다는 식의 검증되지 않은 성능 약속도 하지 않는다.

회사 파일을 사용할 수 있으므로 업로드 자료와 결과의 공개 범위·보관 기간·삭제 방법을 안내한다. 업로드 자료를 공용 예제에 자동으로 추가하거나 다른 사용자에게 보여주지 않는다. AI에 전달되는 내용도 원본 전체가 아니라 작업에 필요한 범위로 제한한다.

공개 서비스로 배포하기 전에는 파일 접근 제한과 보안 점검을 완료한다. 내부 시험이 끝났다는 이유만으로 인터넷 공개가 준비되었다고 표시하지 않는다.

## 10. 성공을 어떻게 판단하는가

가장 중요한 질문은 **“이전에 손으로 하던 주소·코드 작업을 실제 자료로 끝낼 수 있는가?”**다.

웹과 AI에서 동일한 결과를 얻을 수 있는지, 실패한 자료를 찾아 고칠 수 있는지, 결과 파일의 코드가 손상되지 않는지, 기존 시각화 도구가 그대로 동작하는지를 확인한다.

처리 시간과 변환 성공률은 실제 입력 자료·건수·실행 환경·기준 자료 버전과 함께 측정한다. 포트폴리오에는 구현 화면뿐 아니라 규칙, 원천, 실패 처리, 테스트 결과를 함께 보여준다.

> **첫 목표는 ‘모든 공간정보를 한 번에 모으기’가 아니라 ‘주소·코드 작업을 믿고 맡길 수 있게 만들기’다. 그 기반 위에 위치·도형·공공 속성을 차례로 연결한다.**
