# 개발 지시

현재 geo 저장소에 **국내 주소·코드 연계 도구**를 두 번째 프로젝트로 구현하라. 기획 검토만 하거나 골격·가짜 결과만 만든 상태로 끝내지 말고, 아래 1차 범위의 실제 입력 → 변환 → 결과 검토 → 파일 출력 → MCP 이용까지 연결하라.

작업은 현재 체크아웃된 최신 코드와 저장소 지침을 기준으로 한다. 위 커밋은 기획서 작성 당시의 확인 기준일 뿐이며, 더 최신 코드가 있으면 옛 커밋으로 되돌리지 마라.

## 1. 먼저 확인할 것

`git status`와 현재 브랜치·커밋을 확인하고 기존 사용자 수정사항을 보존하라. 저장소의 `AGENTS.md` 등 지침이 있으면 먼저 읽어라. 무관한 변경을 덮어쓰거나 `reset --hard`, 강제 checkout, 전체 데이터 삭제로 작업 공간을 정리하지 마라.

함께 제공된 일반 기획서와 상세 명세를 읽고, 특히 다음 현재 코드의 역할을 재확인하라.

```text
app/utils/projects.ts
app/pages/index.vue
app/components/FlowSteps.vue
app/pages/ai.vue
app/pages/viz/upload.vue
app/components/viewers/

```

현재 구조가 문서와 다르면 실제 코드를 우선 조사하고 변경 이유를 기록하라. 3개 문서가 모두 없더라도 이 명령문에 포함된 핵심 요구로 독립적인 작업을 시작할 수 있다. 다만 읽지 못한 상세 문서를 읽었다고 보고하지 마라.

시작 전에 기존 빌드·검사의 실행 가능 여부와 기존 실패를 기록하라. 전체 공간 샘플·Unreal·모든 변환 레시피를 무조건 새로 돌리지는 마라. 필요한 데이터·도구가 없는 기존 검사 실패와 신규 코드 회귀를 구분하라.

## 2. 구현 의도

원래 목적은 회사 업무에서 쓰는 PNU↔주소 변환을 확장하는 것이다. 시군구·읍면동 등 지역코드의 명칭을 찾고, PNU를 필요한 단계까지 잘라 쓰며, 주소·지역코드·좌표·도형·공공 속성으로 연결하는 도구를 만든다.

기본은 국내 시도·시군구·읍면동·리 체계다. 법정동·행정동·우편번호를 하나의 코드 체계로 섞지 않는다. 건물관리번호를 필수 입력이나 필수 허브로 만들지 않는다.

전체 방향은 주소·지명 / 코드 / 공간데이터 / 비공간 속성 / 위치·좌표라는 다섯 출발점이다. 이번 첫 실행 범위는 그중 **PNU·법정구역 코드·지번주소의 실무형 변환**을 완성하는 것이다. 나머지는 원천 검증에 따라 확장하도록 경계를 잡되 가짜 연계 결과로 채우지 마라.

## 3. 기존 geo와 통합하는 방식

기존 `/viz/**`, `/api/jobs/**`, `/svc/**`, 시각화 도구의 MCP 기능을 유지하라. 새 프로젝트는 `/link`를 기본 경로로 한다. `projects.ts`의 준비 중 항목을 실제 새 프로젝트로 바꾸고, 소개·헤더·AI 안내·메타데이터를 필요한 범위에서 수정하라.

기존 시각화 도구 이름과 확장자별 처리 흐름을 주소 변환 도구 이름으로 일괄 변경하지 마라. 첫 화면에는 두 도구의 목적을 구분해 표시하라. 시각화 카탈로그에서 계산된 통계는 그 의미를 유지하고 새 기능을 레시피 수에 억지로 합산하지 마라.

기존 Nuxt·Vue·TypeScript·Nitro·CSS 환경을 사용하라. UI 라이브러리·서버 프레임워크·SDK를 이유 없이 교체하거나 일괄 업그레이드하지 마라. 필요한 의존성만 유지보수 상태와 라이선스를 확인하여 추가하고 잠금 파일을 유지하라.

주소·코드 로직은 `shared/link/`, `server/services/link/` 등의 별도 도메인으로 구성하라. 기존 `FormatSpec`, `Recipe`, `Job`에 가짜 `address/pnu` 형식을 만들어 Docker 파이프라인으로 우회시키지 마라. 문자열 분해·사전 조회에 지도 서버나 전국 DB를 필수로 요구하지 마라.

## 4. 이번 작업에서 완성할 기능

다음 항목을 하나의 실행 가능한 작업 흐름으로 완성하라. 매 단계마다 승인을 다시 요구하거나 ‘다음으로 진행할까요?’로 멈추지 마라. 실제 권한·인증·데이터 문제에 막힌 부분은 기록하고, 독립적으로 가능한 나머지 작업을 계속하라.

### 4.1 PNU와 법정구역 변환

PNU 19자리 분해, 일반·산 구분, 본번·부번 표시, 지번주소 형식 구성, 법정구역 코드·명칭 조회, 지번주소에서 PNU 형식 조합을 구현하라.

PNU 분해 규칙은 다음과 같다.

```text
법정동코드: value.slice(0, 10)
일반·산:   value.slice(10, 11)
본번:      value.slice(11, 15)
부번:      value.slice(15, 19)
```

core의 일반·산은 1·2로 구분한다. 외부 원천이 다른 값(예: 0·1)을 사용하면 원천 어댑터에서 명시적으로 정규화하고 원본값을 남겨라. 블록·특수지·가번 등을 무조건 일반으로 통합하지 마라.

코드값 전체를 `Number`, `parseInt` 등으로 변환하지 마라. 주소 표시를 위해 4자리 본번·부번의 선행 0을 다루는 것과 전체 식별자를 숫자로 바꾸는 것은 구분하라. 부번 0000이면 주소에 `-0`을 붙이지 마라.

주소 파싱은 지원 범위를 명시하라. 동명에 포함된 숫자, 건물 동·호, 도로명주소 건물번호를 토지 지번으로 잘못 해석하지 마라. 상위 지역이 부족하거나 후보가 여러 개이면 선택 상태로 남겨라. 해석하지 못한 원문 구간은 버리지 마라.

### 4.2 출력 단계와 형태

시도 / 시군구 / 읍면동 / 동·리 / 지번 / 전체 PNU 단계 선택을 제공하라. 코드만, 명칭만, 둘 다, 항목별 분리 출력을 지원하라.

접두 코드 2·5·8·10자리와 사전에 등록된 전체 지역코드를 구분하라. 0을 덧붙였다는 이유만으로 공식 코드 확인을 통과시키지 마라. 임의 앞 N자리 추출은 사용자 지정 문자열 작업으로 표시하라.

코드 출력 단계와 주소 표시 방식은 독립적으로 선택하게 하라. 전체 지역 경로와 최하위 이름, 시도·시군구·읍면동·리 분리 열을 제공하라.

시 아래 구가 있는 경우에는 공식 상위 관계를 따라 시 전체의 하위 구를 포함하라. 특정 도시 이름·코드를 하드코딩하거나 단순 동일 접두어 필터로 시 전체 범위를 대체하지 마라. 리가 없는 동에 가짜 리 명칭을 만들지 마라.

### 4.3 실제 기준 자료

법정구역 사전은 실제 공식 자료를 수집·검증하여 버전과 함께 읽게 하라. 아래 공식 자료를 시작점으로 삼되, 작업 시점의 제공 방식과 인증·이용 조건을 다시 확인하라.

```text
행정안전부 법정동코드:
https://www.data.go.kr/data/15077871/openapi.do
https://www.data.go.kr/catalog/15077871/openapi.json

행정동·법정동·관계 자료 형식 확인 사례:
https://www.mois.go.kr/frt/bbs/type001/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000052&nttId=127979

주소·건물·관련 지번 자료 안내:
https://business.juso.go.kr/jst/jstAddressDownload?menu=7
```

위 행정안전부 게시물을 최신 전국 사전으로 고정하지 마라. 실제 최신 제공 자료와 유효일을 확인하라. 과거 코드·폐지 상태를 현재 코드와 혼동하지 마라.

원천 접근에 키·신청이 필요하면 환경변수·어댑터·설명·검증을 구현하고 누락된 설정을 구체적으로 기록하라. 인증을 우회하거나 개인 정보를 수집하지 마라. 개발용 fixture는 별도로 표시하고 운영 ‘전국 코드 사전’인 것처럼 노출하지 마라.

기준 자료는 `.data/reference/link/` 등 영속 영역에 저장하고 사용자 임시 파일과 분리하라. 작업 시작 때 자료 버전을 고정하라. 신규 수집은 검증 후 활성화하고 실패 시 이전 정상 버전을 유지하라.

### 4.4 목록·CSV·XLSX

직접 입력, 여러 줄·탭 구분 붙여넣기, CSV·XLSX 업로드를 구현하라. 파일에서는 시트·헤더·주소 또는 코드 컬럼을 확인하고 일부 행을 미리 보여줘라.

원본 열·입력 행 ID·순서를 보존하고 결과 열을 추가하라. 실패·빈 값·중복 행을 조용히 삭제하지 마라. 중복 제거와 행 펼치기는 사용자가 선택할 때만 실행하라.

코드 열은 문자열로 보존하라. 이미 숫자로 저장되어 정밀도가 손상된 PNU를 원래 값으로 복구했다고 주장하지 마라. XLSX는 코드 셀을 명시적인 문자형으로 출력하라. 수식·매크로·외부 링크를 실행하지 마라.

CSV 인용·개행·인코딩과 XLSX 숫자 셀을 각각 테스트하라. 스프레드시트 수식 삽입을 방지하고 안전 출력과 내부 원본을 구분하라. CSV의 따옴표만으로 엑셀의 숫자 자동 해석을 막았다고 안내하지 마라.

복사, CSV·XLSX·JSON 출력을 제공하라. 결과에는 기준 버전·출력 옵션·오류 요약을 포함하라. 복수 후보를 펼치면 입력 ID와 후보 ID를 남겨라.

### 4.5 결과·오류의 의미

처리 상태와 확인 수준을 분리하라.

```text
처리 상태: ok / needs_selection / invalid / not_found / unavailable
형식 확인: valid / invalid / not_applicable
코드 확인: active / retired / unknown / not_checked
필지 확인: matched / no_match_in_dataset / not_checked
```

코드 사전으로 주소를 만들었다는 이유만으로 실제 필지 존재를 확인했다고 표시하지 마라. 정상 조회에서 미일치한 경우와 원천 미수집·장애·지원 지역 밖인 경우를 구분하라.

프로그램용 오류 코드와 사용자 설명을 함께 제공하라. 최소한 길이 오류, 구분값 오류, 미등록·폐지 코드, 지역명 모호함, 미해석 주소, 식별자 정밀도 손상, 원천 준비 안 됨을 구분하라.

### 4.6 웹 작업 화면

지도보다 입력·결과 옵션·결과 표를 앞에 배치하라. 기존 CSS 변수와 화면 스타일을 활용하되 결과 표는 긴 주소와 코드를 읽고 복사하기 쉽게 구성하라.

입력 유형 자동 제안과 수동 변경, 단계·열 선택, 진행 상태, 정상·오류·후보 필터, 원본과 결과 비교, 후보 선택, 파일 출력을 구현하라. 빈 입력·처리 중·자료 미설정·오류·결과 없음 상태를 모두 처리하라.

처리 근거에는 실제 사용한 규칙·사전 버전·매칭 방식·경고를 보여줘라. LLM이 꾸며 쓴 설명을 결과 근거로 사용하지 마라.

### 4.7 공통 서비스와 작업 실행

웹 API와 MCP에서 같은 공통 함수를 호출하게 하라. 입력 검증과 출력 계약도 공유하라. 경량 변환을 기존 시각화 `running` 잠금이나 Docker 작업에 묶지 마라.

소량은 동기로 처리하고 파일·큰 결과는 작업 ID를 반환하라. 새 작업 폴더는 `.data/link/jobs/` 등으로 분리하고 기존 `.data/jobs` 정리 함수가 잘못 삭제하지 않도록 하라.

작업 시작 시 기준 자료와 옵션을 고정하고, 중복 호출을 제어하라. 서버 재시작·워커 오류 후 영원히 실행 중으로 남지 않게 하라. 실행 중단 시 실패 표시·재실행만 지원해도 되지만 부분 재개를 구현했다고 과장하지 마라.

초기 제한은 설정 가능하게 하고 상세 명세의 보수적 시작값을 적용하거나 측정 근거로 조정하라. 큰 파일을 동기 요청 하나로 끝내려 하지 마라.

### 4.8 MCP와 MCP Apps

기존 `/mcp` 연결을 유지하고 다음 역할의 `geo_link_*` 도구를 추가하라.

```text
geo_link_capabilities : 지원 기능·자료·한도 확인
geo_link_resolve      : 소량 변환 또는 입력 화면 열기
geo_link_regions      : 지역코드·지역명·하위 구역 조회
geo_link_run          : 파일·일괄 입력 작업 시작
geo_link_status       : 진행·오류 요약·웹 결과 주소
geo_link_export       : 선택 열·형식의 파일 생성
```

도구명은 상세 명세와 맞추되 현재 코드 충돌이 있으면 근거를 기록하고 통일하라. 기존 `geo_identify`, `geo_convert`, `geo_status`, `geo_engine`, `geo_formats` 및 현재 등록된 다른 도구를 삭제·변질시키지 마라.

같은 서버에 새 UI 리소스 `ui://geo/link.html`을 추가하는 방식을 우선 검토하라. 기존 `ui://geo/app.html`은 보존하라. 새 서버·새 연결을 필수로 만들지 마라.

UI는 입력 옵션·후보·미리보기·진행·다운로드를 제공하고 호스트 기능을 감지하라. UI 미지원 환경에서도 도구 호출과 파일·웹 결과 안내가 동작해야 한다. 실제 검증하지 않은 호스트를 지원 완료라고 적지 마라.

현재 패키지·잠금 파일·SDK와 호환되는 방식으로 구현하라. 공식 예제의 최신 의존성 묶음을 통째로 설치해 기존 연결을 깨지 마라. MIME·resourceUri·capability·CSP·다운로드는 실제 설치 SDK와 공식 문서를 함께 확인하라.

```text
https://apps.extensions.modelcontextprotocol.io/api/documents/overview.html
https://modelcontextprotocol.io/specification/2025-11-25/server/tools
```

도구 응답에는 요약·제한된 미리보기·작업 ID·파일 참조만 보낼 수 있게 하라. 전체 파일·긴 코드 목록·전체 도형을 모델 문맥에 무조건 넣지 마라. `structuredContent`가 비밀 저장소라고 가정하지 마라.

채팅 첨부파일을 자동으로 읽을 수 있다고 전제하지 마라. 실제 지원하는 업로드·파일 참조 전달 경로를 구현하고 안내하라. 앱 전용 업로드 도구가 필요하면 권한·크기·순서·재전송을 검증하라.

### 4.9 갱신·보관·공개 안전

일 1회 ‘새 자료 확인’을 실행할 수 있는 명령과 이력을 구현하라. 모든 원천이 매일 갱신된다고 표현하지 마라. 원천 기준일, 확인 시각, 반영 시각을 나눠 보여줘라.

초기 작업 결과 보관안은 24시간으로 두되 설정 가능하게 하라. 접근 시 만료를 확인하고 물리적 삭제는 정기 정리로 수행하라. 코드 사전은 삭제 대상에서 제외하라. 운영 스케줄을 실제 설치하지 못했다면 설치 방법과 미적용 상태를 남겨라.

작업 ID만으로 다른 사용자의 파일에 접근할 수 없도록 권한 모델을 적용하라. 회원 시스템을 크게 새로 만들기보다 현재 배포 방식에 맞는 최소한의 세션·접근권한을 선택하고 테스트하라. MCP 요청과 앱 다운로드의 권한 전달까지 확인하라.

현재 `stageUrl`의 DNS 관련 한계가 해결되지 않은 상태로 새 공개 URL 수집 기능을 확대하지 마라. 첫 버전은 직접 업로드로 제한해도 된다. 로컬 파일 경로는 공개 환경에서 차단하고 사용자 입력을 셸·SQL로 직접 전달하지 마라.

API 키와 원본 회사 자료를 코드·로그·공개 예제에 넣지 마라. ZIP 해제·파일 크기·행 수·실행 시간·외부 API 호출량을 제한하라. 접근 통제나 배포 보안이 미완료면 공개 준비 미완료로 보고하라.

## 5. 기존 지도·확장 기능과의 연결

좌표·도형이 없는 결과는 표 출력만으로 정상 완료다. 기본 PNU 변환에서 가짜 좌표를 만들거나 의도하지 않은 외부 지오코딩을 자동 호출하지 마라.

실제 공간 결과를 얻는 확장 기능을 구현할 때는 기존 뷰어와 파일 변환을 재사용하라. 현재 `/viz/upload`가 `?stage=`를 읽지 않으면 해당 URL만 만들어 연결 완료라고 하지 마라. 서버 권한 확인·파일 복사·명시적인 stage 로딩을 구현하거나, 다운로드 후 업로드하는 실제 동작 경로를 안내하라.

행정동·도로명주소·우편번호·구역 내 전체 객체 목록·공간 검색·공공 속성은 원천이 검증된 기능부터 추가할 구조를 만든다. 이번 핵심 범위를 미루면서 모든 전국 데이터와 모든 지도 기능을 한꺼번에 구축하려 하지 마라.

다만 첫 버전의 프로젝트 설명에서 다섯 입력의 최종 방향을 삭제하거나 ‘PNU 문자열 자르기 전용 도구’로 축소하지 마라. 지원 상태·미지원 이유와 다음 연결 대상을 문서에 남겨라.

## 6. 필수 테스트

순수 도메인 테스트, HTTP·MCP 계약 테스트, 파일 왕복 테스트, 웹 흐름 테스트를 추가하라. `test:link` 등 분리된 명령을 만들고 필요한 테스트 도구만 추가하라.

최소 검증 항목은 다음과 같다.

1. 정상·잘못된 PNU, 일반·산, 부번 0, 길이·문자·구분값 오류.
2. 2·5·8·10자리 출력과 등록 전체 코드의 구분, 임의 문자열 추출 표시.
3. 미등록·폐지 코드, 동명이인 지역, 상위 지역 부족, 리 없음·리 누락, 시·일반구 계층.
4. 법정동·행정동 혼동 방지와 복수 후보, 도로명·동호의 지번 오인 방지.
5. CSV·XLSX의 19자리 문자열·앞자리 0·정밀도 손실·인코딩·개행·수식성 값.
6. 원본 행·순서·중복·실패 유지, 후보 펼치기의 입력 ID, 데이터 미확보와 미일치 구분.
7. 웹·MCP의 결과·오류·버전 일치. 실행 시각·UUID까지 같아야 한다고 비교하지 않는다.
8. MCP Apps 리소스·도구 연결, 화면 미지원 대체 경로, 업로드·다운로드·웹 열기 오류.
9. 작업 중 사전 갱신, 중복 요청, 수집 실패 후 이전 버전 유지, 중단 작업 복구.
10. 권한 없는 작업 조회·다운로드, 만료, 과대 파일, 경로 조작, 로컬 파일 접근 차단.
11. 기존 `/viz`, `/ai`, `/mcp` 도구 목록과 기존 파일 변환 흐름의 회귀.
12. 코드 사전 확인만으로 실제 필지 확인 상태가 되어서는 안 된다는 테스트.

`npm run build`와 새 테스트를 실행하라. 기존 `npm run check`는 카탈로그와 실제 산출물에 의존하므로 실행 가능 조건과 결과를 별도로 보고하라. 실패를 숨기기 위해 검사 코드를 삭제하거나 모든 검사를 성공 처리하지 마라.

지원되는 브라우저 테스트 환경이 있으면 실제 입력 → 옵션 → 결과 → 파일 다운로드를 검증하라. 실제 AI 호스트 실행이 불가능하면 MCP 프로토콜·리소스 검증과 호스트 실측을 구분해 기록하라.

전국 모든 변환 레시피, 대규모 자료 수집, Unreal 렌더링은 이번 변경 검증에 필요한 경우만 실행하라. 테스트를 했다는 표시를 위해 불필요한 장시간 작업을 만들지 마라.

## 7. 문서화와 완료 보고

가능하면 3개 기획 문서를 `docs/link/` 아래에 저장하고 구현과 달라진 내용을 갱신하라. 저장소 README, `/ai` 안내, 환경변수 예시, 실행·테스트 명령, 실제 지원 기능·자료 상태를 업데이트하라.

`docs/link/implementation-report.md` 또는 기존 보고 관례에 맞는 파일에 다음을 남겨라.

- 실제 시작 커밋과 변경 파일·핵심 결정.
- 구현된 기능과 원천·권한 때문에 아직 활성화하지 못한 기능.
- 기준 자료의 제공처·버전·확보 범위와 테스트 fixture의 구분.
- 실행한 명령·테스트 건수·성공·실패·미실행 사유.
- 웹·MCP·MCP Apps 각각의 검증 수준과 재현 방법.
- 측정한 성능의 입력 크기·실행 환경·조건.
- 공개 배포 전 남은 점검과 필요한 설정.

최종 답변은 ‘무엇을 구현했고 어떤 방식으로 확인했는지’로 보고하라. 구현 계획만 반복하지 마라. 실패하거나 미검증인 부분은 실제 상태대로 적되, 한 원천이 막혔다는 이유로 가능한 코어 작업까지 중단하지 마라.

사용자가 승인하지 않은 원격 push·운영 배포·유료 API 사용·권한 확대·DB/볼륨 삭제는 하지 마라. 로컬 개발·테스트 범위 안에서 작업을 완결하라.

## 8. 완료의 정의

**사용자가 PNU·지역코드·지원하는 지번주소 목록을 넣고 원하는 단계의 코드·명칭을 선택하면, 원본을 보존한 실제 결과와 오류 사유를 웹과 MCP에서 동일하게 받고 CSV·XLSX로 가져갈 수 있어야 한다.**

실제 기준 자료가 준비되었는지, 단순 형식 변환인지 원천 기록 확인인지, 앱 호스트에서 직접 검증했는지까지 구분해 보여주는 상태가 완료 기준이다. 기존 geo 시각화 기능은 그대로 사용할 수 있어야 한다.
